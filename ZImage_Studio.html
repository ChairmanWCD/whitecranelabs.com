01 — The brief

Text-to-image at studio cost

Creative teams need to generate images. Cloud APIs make that easy — until you hit the wall of cost, latency, data privacy, and wait times at scale. Every generation is accounted, every prompt leaves the machine, every call competes for a shared queue.

The alternative is running open-weight models yourself. For a long time that meant Docker, Linux, and a bank of data-center GPUs — infrastructure a small studio simply doesn't have.

The question wasn't "can we use a text-to-image model?" It was: "Can a single consumer GPU become a serious, always-on image generation service?"

This project says yes — by porting a production-grade server to native Windows and sharing the models ComfyUI already has on disk.

Rate limits, usage quotas, dependency on a vendor's roadmap.
Option B: Local server
One-time hardware investment
Full data sovereignty — runs on-device
Your own queue, your own timing
Zero per-image cost. Unmetered. Always yours.

Z-Image Studio is Option B, made practical: a self-hosted inference service on a 12 GB mid-range GPU. The hard engineering is making that much model load into that little VRAM.

03 — The architecture

A FAL.ai-style async queue

Generation is slow. UI's must never wait on it. The core design mirrors FAL.ai's pattern: submit a job, poll for status, fetch the result. The interface stays instant while a background worker owns the heavy inference.

Submit, poll, fetch. The UI never blocks on a generation.

Async flow
POST /submit → returns a request_id · GET /status/{id} → IN_QUEUE / IN_PROGRESS / COMPLETED · GET /result/{id} → the images, seed, and timings.

Two APIs, one engine

  • Async queue API — /submit → /status → /result, plus /cancel. Built for polling clients and parallel workloads.
  • Sync API — POST /generate returns the result inline, with optional sync_mode for base64 data URIs.
  • Support endpoints — /health, /api/history (recent images), /output/{file} (static files), and Swagger docs at /docs.

A warmup inference runs at startup so the first real request doesn't pay the cold-start cost. Queue depth is capped (MAX_QUEUE_SIZE), failed jobs retry, and completed results expire after a TTL.

04 — The hard problem

Getting 20 GB of weights into 12 GB of VRAM

Z-Image-Turbo's full pipeline is heavy. The three weight files total nearly 20 GB, but the RTX 5070 has only 12 GB. Nothing fits all at once — so the design treats VRAM as a shared, rotating resource.

How it stays under the ceiling

  • CPU offload — enable_model_cpu_offload() keeps only the active module in VRAM; the rest lives in system RAM.
  • Attention + VAE slicing — both enable_attention_slicing() and VAE tiling/slicing cut peak memory.
  • Auto-downscale — any requested size is clamped to MAX_IMAGE_SIDE (default 1024) before generation.
05 — Porting to Windows

From Docker to a single PowerShell prompt

The original build was Linux/Docker on a data-center Grace Blackwell GPU. Bringing it to a personal RTX 5070 meant removing Docker, scripting the setup, and fixing every quirk that surfaced along the way.

  • Docker removed — Dockerfile / docker-compose archived. Replaced with setup.ps1 (venv + deps) and start.ps1 (uvicorn launcher).
  • Shared model folder — start.ps1 defaults LOCAL_MODELS_DIR to ComfyUI's shared folder — no duplicate ~20 GB download, both tools share one set of weights.
  • VRAM-safe on 12 GB — the offload and slicing fixes above, driven by the fact that ZImagePipeline doesn't expose pipeline-level VAE tiling (an early build errored on exactly that).
  • Windows-friendly paths — config.py auto-detects a ../models sibling folder instead of a container path; output defaults to .\output.
  • Environment — torch cu130 (fallback cu128), diffusers from git main, transformers 5.x. Verified: torch 2.13.0+cu130, cuda=True.

One machine. One script. Your own image generation service.

06 — The interface

A studio-grade web UI

A server is only useful if people can drive it. The bundled single-page UI gives a full generation workspace with a dark, lavender-accented theme — and a light mode for bright studios.

  • Prompt controls — textarea with example chips and Cmd/Ctrl+Enter to generate.
  • Size presets — six aspect ratios from Square HD to Landscape 16:9, all clamped to fit VRAM.
  • Advanced settings — negative prompt, guidance scale, seed + randomize.
  • Output control — inference steps (1–10), image count (1–4), PNG/JPEG.
  • Live feedback — elapsed timer, skeleton loading, cancel, health status, and a /api/history strip to reopen recent work.
07 — What's still hard

The tradeoffs

Local inferencing isn't a free lunch. Being honest about the ceilings is part of the point.

01

VRAM is a hard ceiling. Every optimization exists because 12 GB isn't much for this pipeline. Larger images are impossible without downscaling or a bigger card.

02

Models must be present. The ~20 GB of weights need a LOCAL_MODELS_DIR or a HuggingFace download, and gated repos demand an HF_TOKEN.

03

Windows friction is real. PowerShell's execution policy blocks .ps1 scripts until you bypass or relax it — a classic first-run stumble.

04

First request is slower. Kernel recompilation at larger sizes costs a few extra seconds; steady-state is fast but the warm-up is visible.

08 — Why this matters

Generative infrastructure, owned

Serious creative tooling shouldn't require a cloud subscription. It should run on hardware a studio can actually afford.

Z-Image Studio is a proof that a consumer GPU — not a lab, not a data center — can power a real, queue-based image generation service. It's fast, it's local, and it reuses the models a studio already has through ComfyUI. No per-image fees. No prompts leaving the machine. No vendor in between.
