01 — The brief

One repo, two jobs

I split my old art-director setup into two roles that actually fit how I work: studio-designer owns visual direction and generation, studio-engineer owns build and verify. One repo holds both: the studio and its engine.

The question I kept hitting: "Can my own RTX card become a serious, always-on studio — not a cloud tab I rent by the image?"

WCD Creative Studio is my answer: an art-direction practice backed by a single-engine Z-Image-Turbo server I run myself. I direct, I generate, I ship.

02 — Build vs. buy

Owning the engine

Option A: Cloud API
Per-image pricing + latency per call
Prompts and outputs leave your machine
Shared queue; wait times under load
Rate limits, usage quotas, dependency on a vendor's roadmap.
Option B: Local engine
One-time GPU you already own
Full data sovereignty; runs on-device
Your own queue, your own timing
Zero per-image cost. Unmetered. Always mine.

I chose Option B and made it practical on a Mac mini M4, 32 GB: a self-hosted single-engine service running on Apple Silicon MPS. The hard part isn't the model; it's staying memory-safe while I art-direct at full speed.

03 — The architecture

Submit, poll, fetch, with presets

Generation is slow. My UI never waits on it. I mirror the FAL.ai pattern: submit a job, poll for status, fetch the result. My interface stays instant while a background worker on my Mac mini owns the heavy inference. This is the contract my studio calls; the generation server runs on Apple Silicon MPS via white-crane-generation.

Queue presets, not guesswork. My UI never blocks on a generation.

Async flow
POST /submit → returns a request_id · GET /status/{id} → IN_QUEUE / IN_PROGRESS / COMPLETED · GET /result/{id} → the images, seed, and timings.

Queue presets keep me fast

  • Async queue API: /submit → /status → /result. Built for polling clients and parallel batches.
  • Sync API: POST /generate returns the result inline, with size presets (square_hd, portrait_4_3, portrait_16_9, landscape_4_3, landscape_16_9) or custom width/height.
  • Support endpoints: /health (model readiness), /api/history (recent images), /output/{file} (static files), Swagger at /docs.
  • Two engines, one resident: Z-Image-Turbo (T2I) + FLUX.2 Klein 9B (I2I). ComfyUI-style swap keeps one pipeline resident — no dual-model juggling, no surprise OOM. Presets stay memory-aware.

I cap queue depth, retry failed jobs, and expire completed results after a TTL. Presets do the sizing discipline so I don't OOM mid-batch.

04 — How the studio works

Agents direct, skills constrain, MCPs supply

The engine is only half of my studio. The other half is how I run it: an art-director orchestrator routes every brief to two specialists: studio-designer owns visual direction and generation, studio-engineer owns build and verify. Taste and checks come from vendored skill libraries, icons arrive over MCP, and nothing ships without green verify logs.

The three agents

  • art-director: clarifies the brief, classifies design-only / build-ready / image-gen, delegates via Task, reconciles with explicit deltas, approves on brand + logs. Never edits directly.
  • studio-designer: consults local vendor knowledge, checks GET /health, submits POST /submit, polls, fetches, saves under studio/dist/, inlines Lucide SVGs, returns prompts, seeds, sizes, and handoff notes.
  • studio-engineer: Discuss → Map → Decompose → Execute → Verify; keeps the API contract intact with py_compile / pytest plus curl /health, returns diffs + logs.

Skills and MCPs

  • wc-* skill wrappers: wc-brand, wc-ui, wc-image-gen, wc-decks, wc-eng-backend, wc-eng-verify, wc-eng-ops — brand tokens first, then craft rules.
  • Vendored libraries: open-design systems, templates, and craft plus engineering QA skills, pinned offline so I work with no cloud dependency.
  • mastericons MCP: Lucide line icons, recolored to brand tokens, inlined as SVG. Every icon on this page arrived that way.

Two repos, one call

My studio doesn't host inference; it calls it. WCD-Creative-Studio briefs, prompts, verifies, and ships; white-crane-generation queues, infers, and serves files. Both speak the same FAL-style contract, so I can point my studio at any box running the generation server: RTX or Mac, local or LAN.

Studio → generation call
designer: POST {gen}/submit {prompt, image_size, seed} → request_id · poll GET {gen}/status/{id} → COMPLETED · fetch GET {gen}/result/{id} → save studio/dist/ · engineer: curl {gen}/health → ship.
  • Caller: WCD-Creative-Studio: agents, skills, briefs, verify, ship.
  • Callee: white-crane-generation: Z-Image-Turbo text-to-image + FLUX.2 Klein image-to-image, async queue, static files.
05 — The hard problem

Mac mini M4, 32 GB — unified memory strategy

Z-Image-Turbo is ~19.8 GB on disk; FLUX.2 Klein 9B is ~40 GB in HF cache. On Apple Silicon, unified memory means I treat the 32 GB pool as one resource: MPS offload streams weights between system RAM and GPU, and MAX_IMAGE_SIDE 1024 caps the peak activation memory.

Z-Image-Turbo weights
~19.8 GB
diffusion + text encoder + VAE, bfloat16
FLUX.2 Klein 9B (I2I)
~40 GB cached
auto-downloaded, gated; swap keeps one engine resident
Unified memory pool
32 GB
shared CPU/GPU - unified memory pool
Activation ceiling
1024
MAX_IMAGE_SIDE — presets snap inside it

How I stay under the ceiling

  • MPS offload + bfloat16: weights stream from system RAM to GPU per step; native dtype is stable on MPS.
  • MAX_IMAGE_SIDE 1024: longest edge never exceeds 1024 px. Presets (1024×1024 down to 768×1344) chosen to respect it.
  • ComfyUI-style engine swap: only one pipeline resident at a time (Z-Image or FLUX Klein). Keeps memory pressure predictable on 32 GB.
  • PYTORCH_ENABLE_MPS_FALLBACK=1: falls back to CPU for unimplemented Metal ops instead of crashing.
06 — Running it

From setup.ps1 to localhost:8100

I wanted zero ceremony: no Docker, no CUDA archaeology. Two scripts and I'm live on the machine I already own.

  • Install once: setup.ps1 creates the venv, installs deps, and pulls the ~19.8 GB Z-Image-Turbo weights.
  • Start daily: start.ps1 boots FastAPI + uvicorn on localhost:8100. Ctrl+C to stop.
  • Warm by first prompt: a startup warmup pays the cold-start cost once so my first real generation is fast.
  • LAN-ready URLs: result URLs auto-detect LAN IP, so I can pull outputs from any device on my network.

Two scripts. One port. My own studio, always on.

07 — The interface

A static UI with docs built in

A server is only useful if I can drive it fast. My bundled static UI is a single working surface: prompt, preset, generate; every click maps 1:1 to the HTTP API.

  • Prompt first: textarea with example chips, Cmd/Ctrl+Enter to generate; seed + randomize when I need a keeper.
  • Size presets: five memory-aware presets (Square HD → Landscape 16:9) plus custom width/height, all snapped inside MAX_IMAGE_SIDE 1024.
  • Advanced when I need it: negative prompt, guidance scale, inference steps (1–10), num_images (1–4), PNG/JPEG output.
  • Live feedback: elapsed timer, skeleton loading, cancel, health status, and a /api/history strip of recent outputs.

The API

Everything my UI does is also available over HTTP — an async queue for real work, plus a synchronous endpoint for quick calls. Interactive Swagger lives at /docs.

Async flow
POST /submit → request_id · GET /status/{id} → IN_QUEUE / IN_PROGRESS / COMPLETED / FAILED · GET /result/{id} → images, seed, timings.
  • Sync generation: POST /generate returns the result inline for single-shot calls.
  • Operational: GET /health checks readiness; GET /api/history lists recent images; GET /output/{file} serves static files.
  • Parameters: prompt (required), image_size (preset or custom), num_inference_steps (1–10), guidance_scale (0–20), negative_prompt, seed, num_images (1–4), output_format (PNG/JPEG).
08 — What's still hard

Mac memory knobs I actually turn

Local inferencing on 32 GB unified memory isn't a free lunch. When a generation gets heavy, I reach for the same knobs in the same order.

01

Longest edge first. If I smell memory pressure, I drop MAX_IMAGE_SIDE below 1024 or pick a smaller preset. Pixels are the dominant activation cost.

02

Batch of one. I keep num_images: 1 while art-directing, then scale to 2–4 only for the final keepers.

03

Fewer steps. Turbo is built for low steps; I stay at the low end of 1–10 and only push higher when the composition earns it.

04

Offload stays on. MPS offload is non-negotiable on 32 GB. Turning it off for speed is how I OOM; I leave it on.

05

Swap engines, don't stack them. Z-Image and FLUX Klein each need ~20 GB resident. I never run both — swap via app.py instead.

09 — Why this matters

Shiba-cafe-deck proof

Serious creative tooling shouldn't require a cloud subscription. It should run on hardware a studio already owns.

My proof is small on purpose: a shiba-cafe-deck: a full set of on-brand images generated locally, art-directed and iterated like client work. Same prompt discipline, same preset logic, same queue. If it holds for a deck, it holds for a campaign.

That's the studio+engine loop I wanted: I direct the concept, my Mac mini renders it, and the prompts never leave my machine. No per-image fees. No vendor in between.
